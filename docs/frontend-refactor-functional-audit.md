## Reviewed movement and lifecycle contracts

- Checkout always attributes the authenticated native staff account. Responsible owner, current borrower, registered home and observed location remain separate.
- Scan checkout/return uses one input source, a queue of 1–100, explicit review and explicit confirmation. Both tagged and untagged manual selections retain exact tag/version guards, including a null tag. Return requests also retain exact loan IDs. A repeated scan stages selection; it does not submit.
- Save and read back the original pending request before transport. An uncertain result freezes its captured request ID and payload. Retry resolves only that attempt, never the rest of a queue or a later loan. Verify the receipt before declaring success or consuming reviewed rows.
- Return placement is optional dated evidence, separate from home. Working inventory must not accept a live placeholder as verified placement. A stale room requires a new explicit room/unspecified choice.
- Intake is demo-only. Scanning creates durable drafts, not registered assets. Each entry retains its common configuration, model evidence and device scan time. Confirmed server creation supplies the permanent ID, registration time and default Sydney service date. Selected/all processing consumes successes, retains rejected/unselected entries and stops at an uncertain item.
- Preserve the existing exit distinction: Intake permits explicit exit with a complete preserved queue/request; Scan and Removal block exit while a request is unresolved. A shared exit component must preserve these different rules.
- Staff and administrators may scrap or permanently remove eligible active assets after loans are returned. The reason is optional. Recovery applies only to Scrapped and retains identity/history. Permanently removed is terminal. Administrative permanent deletion of Scrapped is a separate reviewed action with explicit `DELETE` confirmation; never conflate it with retirement.
- Lifecycle actions retain authority/version/tag/no-active-loan guards, immutable outcomes and exact retry. An ineligible selected set is not silently reduced. More than 100 selected assets may be exported but not submitted as a single action. Verified success remains confirmed if refresh or local recovery cleanup fails.

## Existing limitations and review risks

- In the frozen baseline, initial sign-in session-load failure leaves inputs disabled and exposes an error without a dedicated in-page retry. The refactor adds a retry action verified by the independent sign-in probe. This was a baseline recovery limitation, not a refactor regression.
- Task-cycle completion retains its uncertain attempt in mounted component state; detail charging/observation/correction retains a request signature in a ref. These do not provide the same persistent recovery guarantees as scan/intake/movement. Avoid remounting them during pending work. These are source-inspected risks, not reproduced losses.
- Task-plan editing also retains its request signature in mounted component state, unlike new-plan creation's persistent request capture. Preserve current conflict review and do not add automatic dismissal.
- Task generation occurs when the application is used; unattended/email delivery is not implemented. Preserve capability wording.
- `docs/permissions.md` already records shared metadata for personal-message audit events, remaining legacy administrator people-write API paths, and authority-dependent recovery after administrator demotion. These are existing documented limitations.
- Narrow-screen cards must preserve every operation, selection rule, identity, relevant evidence and status currently available through the table. Browser event and accessibility verification is required.
- Dynamic reduced-motion cancellation was incomplete in the original baseline: a running `spring` or `transitionWorkspace` could finish after the preference changed. Those implementations remained unchanged through the structural batch. The later polish increment adds runtime listeners and verified settlement/cleanup for these helpers and ReceiptAction; its 23-case shared-motion and 10-case receipt probes are recorded below. Existing `observeWorkspaceMotion` and `dismissOverlay` already listened for changes. These controlled results do not certify every browser CSS transition or event sequence.
- In the verified after-5 ScanStation baseline, reaching the 100-item limit inside manual batch selection could set a warning and then overwrite it with generic added-selection guidance. The first notice-tone increment retained that pre-existing sequence. The subsequent capacity flag now preserves the warning, with 11/11 actual callback/source checks against the final unchanged ScanStation. This corrects an existing presentation defect without changing accepted batteries, queue limits or request guards; see `polish-scan-capacity-review.md`.
